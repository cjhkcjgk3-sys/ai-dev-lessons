# AI 写代码踩坑经验库

这里记录 AI（GPT、Codex、Gemini、Claude、Grok 等）帮我写插件时**真实踩过的坑**：出了什么问题、为什么会出、怎么解决、以后怎么预防。每一条都附证据（提交链接、文件位置或我的原话），不写猜测。

目标不是让模型不犯错，而是**少犯低级错误、不重复犯同类错误**。

## 给 AI 的规定（先读这里）

1. **开工前读完整个 [`正式/`](正式/)**：通用准则、检查清单、工作流程、全部模型专项（不只读自己那份）、相关案例。可以 `git clone https://github.com/cjhkcjgk3-sys/ai-dev-lessons`，或看网页版。
2. **按 [工作流程](正式/工作流程.md) 干活**：开工汇报写相关条目编号；大改先发方案确认；同一问题修到第三次停下重新设计；边做边记；版本更新在 CHANGELOG 署名；收尾发交付汇报。
3. **只有 `正式/` 算规则，而且是所有仓库开发规则的唯一权威。** 各仓库的 AGENTS.md、`docs/开发准则.md` 只补充本仓库专属内容，冲突时以本仓库 `正式/` 为准；[`待审/`](待审/) 里的内容只供参考。
4. **不要直接改 `正式/`。** 新经验、修改意见一律交到 `待审/`，由用户审核。

## 目录结构

```

模板/                 交付汇报、问题记录（小／大）、方案确认、重新设计、待审条目

```

## 通用问题和专门问题

- **通用问题**：写任何代码都可能遇到的，比如没升版本号、测试替用户滚动、状态不联动、没问就改设计。交到本仓库 `待审/`。
- **专门问题**：只在某个插件里出现的，比如世界书配对规则、某个酒馆接口的怪癖。记在那个插件仓库自己的问题记录里。
- 拿不准的先记在插件仓库，标“可能通用”。通用问题不两边重复写，插件仓库只留一行链接。

## 署名

署名写在各插件仓库的 `CHANGELOG.md` 里：谁做正式的版本更新或合并，谁就在那个版本下写“更新人：家族名”（Grok、GPT、Gemini、Claude、DeepSeek，用户自己改的写 human），不写型号。只读、审查不用署名；从下一次版本更新开始执行，以前的不补、不追查。本仓库只记问题和解决方法，不记署名。

## 审核机制

- 审核人是用户，或用户指定的模型代审，最后由用户确认。结果分通过、合并、驳回三种，见 [待审/README.md](待审/README.md)。
- 把内容并入 `正式/` 的提交，说明里要写“审核通过”；只有用户或指定审核人可以这样写。
- 待审积压超过 20 条或最早一条超过两周，提醒用户集中审一次。

## 自动检查

[`.github/workflows/check.yml`](.github/workflows/check.yml) 在每次推送和合并请求时检查：改动 `正式/` 的提交，说明里必须有“审核通过”。

不通过会标红，但**不会拦住直接推送**。真正拦住需要在仓库设置里开分支保护（要求合并请求、要求检查通过、要求 CODEOWNERS 审批）；[`.github/CODEOWNERS`](.github/CODEOWNERS) 已写好 `/正式/ @cjhkcjgk3-sys`。开了分支保护后就不能再直接推 main，所以目前没有开，是否开由用户决定。

## 使用环境（写代码时要考虑）

- SillyTavern 1.19，插件经 GitHub 仓库链接安装。
- 手机端是 SillyDroid（Android WebView，触屏）；电脑端是浏览器。两端都要能用。
- 用户习惯让 AI 直接推送到 main，不要强推；大改动、删功能、改布局前先问。
