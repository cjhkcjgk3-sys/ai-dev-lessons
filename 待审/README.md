## 提交

1. 先说明候选会改变的具体判断或行动以及依据，查相关正式、待审和[已驳回](已驳回/)条目，确认实质增量。建议实质修订已有条目时，指向原 ID，写清对义务、适用范围、效力或处理结果的影响。
2. 一条一文件，文件名 YYYY-MM-DD-模型-简题.md，按[模板](../模板/待审条目.md)写清范围、性质、核心经验、实际用途、来源/模型贡献、确认与证据状态、适用条件。软件开发经验补充错误模式、预防步骤和验收；其他类型按实际内容调整，不为了格式编造。
3. 项目专属写项目记录；具体工具版本细节归[技术参考](../技术参考/README.md)。本仓库公开，只写在用户持续授权范围内适合公开的非敏感内容；正常提交、合并及符合准入的归档不重复确认，未授权公开的内容不写入；必要的原意与模型解释可以匿名化转述，不上传私密聊天或原始日志。仍有重大歧义的灵感留在可见上下文或授权私有候选区，不混入正式索引。

## 审核

用户可以审核决定；任何模型也可以独立复核其他模型的候选，指出遗漏、给出反例、修改或形成有依据的共识。明确已获用户认可的经验，或经实际独立复核、适用范围和依据清晰且无未决实质分歧的非强制经验，可晋升并记录真实确认状态；模型复核不等于用户审核。缺少独立复核且未获用户认可的新思想可保留待审，不阻塞工作。新增或改变用户硬性要求仍由用户决定。用户认可、模型共识、事实验证和规则效力分别判断。实际验证后按[跨模型验证互认与继承](../正式/仓库规范.md#跨模型验证互认与继承)添加简洁的验证记录，其他模型可在适用范围内复用；标记数量不自动决定晋升。

| 结果 | 处理 |
| --- | --- |
| 通过 | 并入对应正式分类，注明实际审核/复核模型、日期、范围、性质、依据与原记录，更新索引后移出待审 |
| 合并 | 加强已有正式条目，保留 ID 和来源，更新索引并移出待审 |
| 驳回 | 移至 已驳回/，写明理由，防止重复提交 |
| 需澄清 | 保持待审，注明具体缺口，不默认生效 |

每次提交、修改、复核晋升、合并、驳回或恢复都同步追加 [CHANGELOG](../CHANGELOG.md)，采用[修改留痕模板](../模板/修改留痕.md)。不再以提交说明包含“审核通过”作为正式区修改条件；只有确有用户批准时才称用户审核通过。待审积压超过 20 条或最早一条超过两周时，在实际维护节点集中复核：已有充分依据且符合准入的可合并或晋升；重复、失效或失去实际用途的按原因归档，保留原稿与恢复路径；仍有价值但证据不足的注明具体复查条件。年龄仅是复查触发，不是自动失效期限；不为此设置后台监控，也无需逐条打断用户。
