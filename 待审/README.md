## 提交

1. 先查相关正式、待审和[已驳回](已驳回/)条目，确认新增价值；能加强现有条目就明确指向，不重复全文。
2. 一条一文件，文件名 YYYY-MM-DD-模型-简题.md，按[模板](../模板/待审条目.md)写清范围、性质、核心经验、实际用途、来源/模型贡献、确认与证据状态、适用条件。软件开发经验补充错误模式、预防步骤和验收；其他类型按实际内容调整，不为了格式编造。
3. 项目专属写项目记录；具体工具版本细节归[技术参考](../技术参考/README.md)。本仓库公开，只写经用户明确授权公开的安全内容；必要的原意与模型解释可以匿名化转述，不上传私密聊天或原始日志。仍有重大歧义的灵感留在可见上下文或授权私有候选区，不混入正式索引。

## 审核

审核人是用户或指定代审模型（最终用户确认）；用户明确授权“复核无问题后转正式”时，仅在该次范围执行并留下记录。用户对思想的认可、事实验证、正式晋升与规则效力四者分别判断。

| 结果 | 处理 |
| --- | --- |
| 通过 | 并入对应正式分类，注明审核人、日期、范围、性质及原记录，更新索引后移出待审 |
| 合并 | 加强已有正式条目，保留 ID 和来源，更新索引并移出待审 |
| 驳回 | 移至 已驳回/，写明理由，防止重复提交 |
| 需澄清 | 保持待审，注明具体缺口，不默认生效 |

正式区变更的提交说明须含“审核通过”，且确有用户审核授权；CI 字符串检查不代替授权。待审积压超过 20 条或最早一条超过两周，提醒用户集中审核；无需逐条打断。未经授权不改正式区、不把一次授权当永久授权。
