# 经验知识库规范（V2.2）

## 目的与责任

积累能改善未来模型判断、设计、创作、执行或验收的有效经验，让用户不必反复重述。经验萃取负责主动发现、还原、筛选、归类、按需检索和运用；仓库负责稳定的内容、范围、状态、索引和历史。未安装技能的 Agent 同样按本规范工作。

## 适用范围与效力

- 普适经验：在不同专业领域都成立；领域经验：特定专业内跨项目复用；专项经验：某类具体任务或产品内复用；项目专属：依赖特定项目、功能、版本或环境。选择证据和讨论支持的最窄充分范围；可用标签关联，不复制正文。来源场景不决定适用范围。
- 正式表示当前可采用的经验正文，包括用户审核通过的原始经验和留痕的模型修订、复核晋升；不表示全部经用户逐条确认，也不表示所有内容都应成为硬性命令。记录分别标注强制规范、指导原则、方法论、实践/避错经验、创新思想、技术知识等性质和适用条件。既有已审核开发规则保持原效力，软件开发规则不自动用于其他领域。只有适用的强制规范必须遵守；指导经验结合当前目标运用。规则冲突按下节统一裁决，不静默扩大授权。
- 正式/ 是共享规则与当前有效经验的权威来源；项目文档补充项目约束。具体案例只作案例证据，技术参考按版本复核；待审/ 不是正式规则。

## 规则优先级与冲突裁决

先判断规则是否适用于本次任务的领域、专项、项目、阶段和实际风险；不适用的规则退出比较，不能只因位于正式区就强行套用。按下列顺序处理真正冲突的适用规则：

1. 宿主系统规则、安全、真实权限及隐私边界。经验库不能授予技术权限，不能越过这些边界，也不能以历史经验替代当前事实。
2. 用户本次明确目标、授权范围和已确认的项目硬性要求。只有用户明确改变同一要求时才更新其旧决定；含糊的新话不能自动推翻明确旧约束，模型共识也不能。已授权的同一范围不重复请示；未获授权的实质变更另行确认。保护数据、诚实报告、停止无依据反复修复等硬性底线不因赶进度或一般性“继续”而跳过。
3. 本库现行治理规范：经验权限、公开边界、审核状态、留痕、冲突处置。它裁决仓库维护问题；软件项目开发流程裁决项目内实现问题，不将项目的版本发布流程套给经验库文档维护。
4. 适用的正式强制规则和已确认的项目约束：共享规范提供底线，项目约束在不违背底线或用户明确要求时作具体化。专项、项目细节不当然高于通用硬性规则；在同等效力的规则间优先采用更贴合实际场景且有充分依据的规定。仍矛盾则说明具体冲突并向用户确认，不自选有利条款。
5. 正式指导原则、方法论、实践及避错经验：以目标、风险、成本、可行性和实际证据决定取舍；有冲突时采用适用性更强的做法并说明关键取舍。避免把建议提升为硬命令。
6. 索引、摘要、模板、案例、模型提醒、技术参考、待审、历史日志：按各自功能辅助定位、格式、参考或复核；不独立创造更高权限或覆盖现行正文。模板与正文矛盾时按本规范和对应现行正文执行，并修正模板；历史记录保留当时语境，不把旧制度当现行指令。

正文效力以用户确认的具体要求及当前规范为准。索引和兼容摘要若与独立方法正文冲突，查最新修订及依据，以相应正式正文为准并同步修正摘要；不能仅按文件更新时间或模型名判定对错。无法可靠处理的实质冲突，保留原有效做法和分歧，必要时请用户决定。

常见裁决：在已授权目标内完成必要联动和回归属于本次工作，不是擅自扩大范围；无关新功能或不必要重构先报告。复用与 UI 一致性服务用户任务，不得压过必要可用性、数据安全、已确认的不同布局和交互。简单优先不等于省略必要验证或恢复保护。第三次仍失败须停止继续修补，先重新设计并获得确认；不是每个小步骤都要重新询问。验证要求随实际改动范围和风险适用，文档变更不套用代码发布、真实设备或插件版本检查；适用但未执行的必需发布验证不能靠填“未验证”绕过。

## 发现与准入

在实质性工作开始或阶段切换时主动继承经验；在有价值的思想形成、明确决定、重要纠正、实践完成等自然节点主动考虑沉淀。日常对话可能产生经验，但不要求每轮总结、每次提交或遍历所有历史。

以完整思想而非句子、轮次或字数为单位。先还原用户目标、原因、适用条件、实际效果，整合有价值的模型解释和后续确认。区分用户原意、模型澄清、模型新增判断、可核验事实及后续纠正；不把用户沉默当认可，不把未经验证的提议写成实测。

写作以把事情说清楚为标准：保留思想、原因、关键做法、必要条件及实际用途；简单经验数句足够，复杂经验按需要展开。不要长篇复述对话、同义反复或为填字段凑字，也不要省略影响理解、判断和应用的内容。不设固定字数。

入库前检查四件事：未来 Agent 能用它做什么；脱离对话是否仍准确完整；范围与状态是否可靠；相比现有正式、待审、驳回条目是否有实质增量。常识只要能改善行为也有价值。废话、附和、纯情绪、重复、空泛口号、临时指令及无依据推断不入库。用户反馈与有依据的预防建议足以进入待审，不要求额外举证或先犯错。未成熟但有价值的思想先在获准的私有候选区或可见上下文保留；有重大歧义时集中确认。

## 归档、审核与权限

- 普适、领域及专项新经验按 [待审](../待审/README.md) 提交与复核；明确范围、性质、实际用途、用户意图与模型贡献、确认状态和证据程度。对现有经验的有依据改进可直接修订，无需绕道待审；不得借修订将实质新增且未达准入条件的思想、扩大适用范围或提高效力的判断直接写成正式规则。成熟度或范围不清、存在实质争议的新增观点先留候选。用户确认、模型复核和事实验证分别记录。
- 项目专属经验写入该项目已有的决策或问题记录，按项目授权操作；不能访问该项目时提供待写入文本，不改放共享正式区。不能确定通用性时先留项目记录标“可能通用”，不把专属细节双写到共享库。具体工具、平台、环境知识进入技术参考（需授权、公开安全且有复核说明）。
- 本仓库当前公开。读取/写入技术权限不等于允许公开用户内容；只有用户明确授权公开的非敏感经验可写入，即使是待审也一样。仅保存足够的匿名化解释与必要来源，不上传聊天全文、私有项目细节、个人敏感信息、密钥或凭据；未获公开授权、可能暴露信息或语义不清时留在可见上下文/获准私有位置。此规则不构成未来自动上传授权。
- 合并、修正、失效均保留历史、原编号或映射；相关增量直接加强原记录，避免同义重复。驳回记录用于防止重复提交，不作为有效规则；有新依据可重新提出。历史技术参考不自动晋升。

## 多模型协作与修改权限

用户允许各模型共同维护本仓库。任何具备仓库写入权限的 Agent 都可以主动修订正文、规范、分类、索引、案例及模板，纠正错误、补充遗漏、改进推理或组织方式；不因前任模型或历史审核而禁止改进。普通修订不需要逐次人工批准，也无需先取得其他模型同意。

修改前读相关原文、日志和依据，判断问题及影响。修改时保留仍有效的要求、来源、必要条件及适用范围；同步相关索引或规则，避免局部改动产生矛盾。模型不得用自己的偏好取消用户明确确立的硬性要求、改变公开授权边界，或把模型判断标成用户已确认。涉及这类实质变更，提出理由交用户决定。

欢迎不同模型独立提出改法和反例，也可直接修正前一模型的明显漏洞。对合理的不同方案，说明取舍与适用条件；有实质争议且不能凭依据解决时，保留可用的现行做法与分歧记录，将争议部分放待审，不反复互相覆盖。记录实际参与复核的模型家族、同意的具体内容和仍有分歧的地方；同一模型自审、沉默、模拟别的模型或重复回答不算独立共识。共识增加采纳依据，但不替代真实验证或用户确认。

## 检索与使用

1. 实质任务开始先读 README、此规范及[总索引](../总索引.md)；辨识领域、专项、项目、阶段与风险。软件开发读取[开发工作流程](工作流程.md)和[通用准则](通用准则.md)。其他领域只读相关入口。
2. 通过索引选读相关正式正文和适用强制要求，遇到阶段变化、新风险或复发再补查。无关领域、案例、所有模型文件及历史不整库读取。索引只定位，不替代适用正文；未读到的关键要求如实说明。既有规则引用旧路径或编号时，循兼容页进入对应正文。
3. 将命中的经验转化为本次具体行动和验收；开发开工报告写相关编号与行动，收尾说明执行/证据/未验证。不为报告凑条目，不能仅列编号当作已落实。
4. 经验库不可访问时继续能做的任务并说明未读取，不能编造命中；不强制为归档开展大规模调查或读取所有历史。遇到需要仓库外权限的工作单独确认。

## 维护与回滚

每次实际修改仓库内容（含新增、修订、合并、驳回、归档或恢复）与 [CHANGELOG](../CHANGELOG.md) 同一次提交；按[留痕模板](../模板/修改留痕.md)新增独立日志，写明日期、修改者（模型家族；用户自己改写 human）、修改范围、修改原因、修改内容和核验状态。重要判断写依据、取舍、未决问题；简单改动简写即可。无需每次改版本号或另建长篇报告；一个合理的原子提交对应至少一条新日志。

Git 记录具体差异、时间与提交身份，日志解释目的和实际改法，两者不可互相替代。保留旧日志原文，只追加新条目（可插在顶部）；更正旧说法用新记录说明。正式正文及索引同次更新、维持稳定 ID 和兼容入口；保留原用户审核与模型后续修订的区别，必要时在正文注明最近实质修改及复核来源。不要强推、不重置共享历史、不覆盖并发修改；有冲突先重新读取，合并或保留分歧。恢复用新的 revert/修复提交并补日志，说明恢复的旧版本或提交及原因，不抹去出错历史。远端写入后核对目标、提交、内容和 CI；如实区分本地、已提交、已推送和已验证。
