# 工作流程（软件开发任务适用）

本页适用于软件项目开发、修复及发布。经验库自身普通文档维护按[仓库规范的协作权限与优先级](仓库规范.md#规则优先级与冲突裁决)，不套用插件发布检查或重复确认。其他领域按[仓库规范](仓库规范.md)使用相关经验，不自动套用开发流程。格式见[模板](../模板/)。

## 开工前

1. 读 [README](../README.md)、[仓库规范](仓库规范.md)、[总索引](../总索引.md)、本页与[通用准则](通用准则.md)。通过[软件工程索引](领域经验/软件工程/索引.md)选读本次适用的方法正文；按任务读取相关[模型提醒](models/README.md)、案例、项目约束和问题记录。不要求整库阅读，不因模型家族不同而跳过相关错误模式。
2. 开工汇报第一句写“已读经验仓库，本次相关条目：……”，并说明这些条目对应的具体行动及验收。未读到的适用要求写明；没有匹配经验时如实说明，不凑编号。
3. 明确实际支持范围；酒馆插件按[通用准则第 2、8 组](通用准则.md)沿用宿主原生 UI 逻辑、默认只适配手机。电脑端等其他适配有明确需求再纳入，不无需求扩大范围，不取消项目既有明确约定。先查复用：本仓库已有代码、宿主原生功能及相关插件或模块的实现；报告查了什么、为何复用或新建。列出影响范围和关联消费者，确定用户预期效果、成功标准与验证方式。涉及多个机制争用同一状态或资源、错误可能穿透到重要操作时，在方案阶段按[方法 08](通用方法.md#method-08)明确功能仲裁，并按[方法 06](通用方法.md#method-06)设计必要的多层防护及对应验收。涉及扫描、递归、渲染、轮询、后台或批量任务时，按[方法 15](通用方法.md#method-15)在方案阶段明确适用的运行边界、资源预算、停止条件、超限处理及目标设备验证，不等出现性能故障再补限制。性能适配明确实际目标设备档位，采用[方法 15](通用方法.md#method-15)的默认基准或已确认的特殊要求；新增或调整多工作区时按[方法 11](通用方法.md#method-11)核算整体可用空间、内容容量及真实任务验证。
   对高风险设计，按[方法03](通用方法.md#method-03)预演失败、先验关键前提；按[方法02](通用方法.md#method-02)衡量复杂度收益，可用[HA-03](普适经验/最小完整闭环再扩展.md)分阶段实现代表性流程。开发 Agent 应用按[专项索引](专项经验/Agent开发/索引.md)选读适用方法，不对普通插件强制增加运行时机制。
4. 大改先提方案：布局、交互、数据格式、删功能等按[方案确认](../模板/方案确认.md)获用户批准；明确已授权的本次重构不需重复确认相同范围。未授权的独立新功能或改变用户已确认契约的改动另行确认；授权目标内为实现功能、保持联动及回归所必需的改动直接完成并说明，不要求逐文件确认。
5. 开始修复前查本项目问题记录、历史提交和用户反馈，识别是否为同一问题的后续尝试；记录原始症状、预期效果、已尝试办法、累计次数及当前假设。不能可靠确定历史次数时标明未知，先补查相关记录，不把它默认为第一次。

## 干活时

6. 边做边记：小问题按[小问题模板](../模板/问题记录-小.md)记录原因、解决和状态；大问题按[大问题模板](../模板/问题记录-大.md)记录完整过程及解法。绕远路的保留直接办法、相关命令/版本/路径/报错；不编造历史。
7. 按任务阶段和新风险补查适用经验。每次修复失败后对照原预期复核根因假设、失败原因及关联场景，不能只把用户反馈中的一个点改好就宣布解决。下一次尝试须说明新依据和如何验证，避免同类补丁循环。三次是停止无效修补的最晚界限，不是可用完的试错配额；已有反例或实际任务验证表明原设计假设不成立时，应立即回到根因分析与方案设计，不必等到第三次。每次修复按原用户目标及关联回归自查，不能把本可自行完成的基本验收交给用户反复指出问题；涉及未授权的实质设计变更仍按第 4 项确认。
8. **同一问题第三次修复仍失败，必须停下继续修改。** 同一用户可见问题或未解决的同一目标按同一问题累计，换模型、会话、文件、分支或症状小变不清零。提交[重新设计](../模板/重新设计.md)，说明前三次结果、已知/未知根因、新方案与验收标准；待用户确认后再继续。记录“修复未验证”而非已解决；无实质依据的新试错不继续。已确认解决后若同类问题复发，仍须查历史并说明关联，不能无依据重置计数。
9. 从用户反馈、共同讨论、实践或有依据的预防分析提炼经验，先按[准入门槛](仓库规范.md#发现与准入)判断是否值得写入共享库。符合准入且获准公开的新经验按[待审模板](../模板/待审条目.md)提交，维护已有经验按[正式区修订边界](仓库规范.md#归档审核与权限)判断。专属问题记项目仓库。通用性不确定先标“可能通用”，不两边重复正文。

## 收尾

10. 可用[交付前快速自检](../模板/交付前快速自检.md)定位遗漏，再逐项核对[检查清单](检查清单.md)中适用项，覆盖用户实际流程和关联回归。区别自动测试、模拟及真实环境；不适用、未验证、失败不得写成通过。改动越大越须执行适用的完整测试，必需发布验证未通过不推送为可用版本；获用户明确授权的未验证交接或修复分支应如实标注。仅文档维护执行相关文档、链接和仓库检查。证据不足不宣布问题解决。
11. 正式版本更新在插件 CHANGELOG 对应版本写“更新人：模型家族名”；只读、审查无需署名。从 2026-11-18 后下一次版本更新开始，不追补历史；其他模型同样只写家族名，用户自己改写 human，不核验历史归属。本经验仓库每次实际修改都按[留痕模板](../模板/修改留痕.md)同步追加日志，无需每次升版本号。
12. 按[主动交付与持续授权](仓库规范.md#主动交付与持续授权)检查、提交、推送及必要的 PR 合并，满足条件后主动完成远端交付，不等待重复授权。确认远端最终状态并处理范围内的问题；受必需检查、第三次修复停止规则、真实权限及不可逆操作确认约束。
13. 长任务中断或跨模型接力时按[HA-02](普适经验/跨模型任务交接.md)及[交接模板](../模板/任务交接摘要.md)传递必要决策、证据与实际状态。必须交[交付汇报](../模板/交付汇报.md)，写明应用的经验和具体结果、修复累计次数、验证与未验证、记录位置、提交链接及签名状态。未涉及的写“无”，未做的写“未做”。

## 正式区与待审区

14. 只有适用的正式强制规则是必须遵守的要求；案例、技术参考和待审不是正式规则。各模型可主动修订现有正式经验及规范，改动同步追加日志；不得擅自推翻用户明确的硬性要求。新经验复核和冲突处理按[待审区](../待审/README.md)与[仓库规范](仓库规范.md)。
