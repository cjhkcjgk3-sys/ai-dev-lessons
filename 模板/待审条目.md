# 待审经验条目模板

一条完整思想一个文件，放入 待审/，命名 YYYY-MM-DD-模型-简题.md。先查重，具体方法应能改变未来 Agent 的判断或行动。用户反馈和合理预防性分析足以提交，不要求用户复现、截图或证明。只保存获准公开的非敏感内容；模型解释须忠实且标识来源。适用字段按需保留，不凑字、不编造。

```markdown
# 简题（具体、可检索）

提交模型：模型家族
建议归类：普适 / 领域（主题）/ 专项（主题）
经验性质：指导原则 / 方法论 / 避错经验 / 实践 / 创新思想 / 建议规范 / 其他
建议新增或修改：相关 ID 或新条目
状态：待审核
用户确认状态：明确 / 已明确采纳 / 未确认 / 不适用
证据状态：推理或预防性建议 / 观察 / 已验证 / 未验证

## 核心经验与实际价值
完整、可独立理解的思想：做什么，为什么，有什么实际用途。

## 适用条件与边界
适用任务、阶段、限制、例外；不能可靠外推时缩窄范围。

## 可执行方法（按需）
如何将思想落实为判断或行动；软件开发条目保留错误模式、可执行预防步骤与验收检查。

## 来源与依据（按需）
用户原意：必要且获准公开的准确短摘，或明确标注的匿名化转述。
模型理解与贡献：澄清、补全逻辑或独立建议，区别未确认推测。
后续反馈、事实、参考/案例：可选，不写无法确定的归属或验证结果。
```

- 旧软件条目仍可沿用“错误模式 / 通用原则 / 可执行预防步骤 / 验收检查 / 可选参考与来源说明”的格式，补充必要范围与状态即可；不强迫创作或方法论经验写虚构错误模式。
- 项目专属不进共享待审；技术细节归技术参考。已确认的用户想法也必须遵守正式审核、公开授权及去重规则。
- 记录最终原则而非长篇对话。不得把模型自己的解释冒充用户意见、把认可冒充实测或把提交流程当正式批准。
