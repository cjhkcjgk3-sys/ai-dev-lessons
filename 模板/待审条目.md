# 待审经验条目模板

一条完整思想一个文件，放入 待审/，命名 YYYY-MM-DD-模型-简题.md。提交前按[准入门槛](../正式/仓库规范.md#发现与准入)查重并判断实际价值。只保存获准公开的非敏感内容；模型解释须忠实且标识来源。适用字段按需保留，不凑字、不编造。

```markdown
# 简题（具体、可检索）

提交模型：模型家族
建议归类：普适 / 领域（主题）/ 专项（主题）
经验性质：指导原则 / 方法论 / 避错经验 / 实践 / 创新思想 / 建议规范 / 其他
建议新增或修改：相关 ID 或新条目
状态：待审核
用户确认状态：明确 / 已明确采纳 / 未确认 / 不适用
证据状态：推理或预防性建议 / 观察 / 已验证 / 未验证
验证：模型家族｜类型｜结果｜日期｜范围/条件｜正文基线｜依据（有真实验证才填写）

## 核心经验与实际价值
说明未来 Agent 在什么情形下会改变哪个判断或行动，以及为什么值得改变。若建议修订已有条目，说明原做法与拟改做法的实际差异。

## 适用条件与边界
适用任务、阶段、限制、例外；不能可靠外推时缩窄范围。

## 可执行方法（按需）
如何将思想落实为判断或行动；软件开发条目保留错误模式、可执行预防步骤与验收检查。

## 来源与依据（按需）
用户原意：必要且获准公开的准确短摘，或明确标注的匿名化转述。
模型理解与贡献：澄清、补全逻辑或独立建议，区别未确认推测。
后续反馈、事实、参考/案例：可选，不写无法确定的归属或验证结果。
```

- 验证标记按[跨模型验证互认与继承](../正式/仓库规范.md#跨模型验证互认与继承)填写；没有验证则省略这一行。记录真实复核及其覆盖范围，不为所有家族预留栏位，不把提交或用户认同当作验证。
- 旧软件条目仍可沿用“错误模式 / 通用原则 / 可执行预防步骤 / 验收检查 / 可选参考与来源说明”的格式，补充必要范围与状态即可；不强迫创作或方法论经验写虚构错误模式。
- 项目专属写回项目，技术细节归技术参考。直接修订与实质改动按[正式区修订边界](../正式/仓库规范.md#归档审核与权限)判断，待审候选按[复核流程](../待审/README.md)处理并标明真实状态。
- 记录最终思想而非长篇对话。以清楚为标准，不追求长或短；必要原因、适用条件和操作含义不可漏。不得把模型解释冒充用户意见、把认可冒充实测或把模型复核冒充用户批准。每次修改按[留痕模板](修改留痕.md)追加日志。
